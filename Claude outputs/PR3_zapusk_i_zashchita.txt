Структура проекта (объектная модель):

profile_settings/
├── README.md
├── requirements.txt
├── main.py
├── storage.py
├── utils.py
├── models/
│   ├── __init__.py
│   ├── users.py
│   ├── profiles.py
│   ├── settings.py
│   └── parameters.py
├── data/
│   ├── users.json
│   ├── profiles.json
│   ├── settings.json
│   └── parameters.json
└── tests/
    ├── test_users.py
    ├── test_profiles.py
    ├── test_settings.py
    └── test_parameters.py

Проект развёрнут в той же папке репозитория, что и ПР2 (поверх
уже закоммиченной функциональной версии), поэтому виртуальное
окружение уже должно быть создано.

1) Открыть папку проекта в VS Code (File → Open Folder...), открыть
   терминал (Ctrl+`).

2) Активировать виртуальное окружение (если ещё не создано — см.
   инструкцию к ПР2, шаг "python -m venv .venv"):

   Windows (PowerShell):
       .venv\Scripts\Activate.ps1

   macOS / Linux:
       source .venv/bin/activate

   Признак успешной активации — приписка (.venv) в начале строки
   терминала.

3) Установить/обновить зависимости (если requirements.txt менялся):

       pip install -r requirements.txt

4) Запустить приложение:

       python main.py

   Появится главное меню:

       1. Показать профили
       2. Показать настройки профиля
       3. Показать параметры настройки
       4. Добавить настройку
       5. Добавить параметр
       6. Изменить значение параметра
       7. Сбросить параметр к значению по умолчанию
       0. Выход

5) Чтобы выйти из виртуального окружения после работы:

       deactivate

ЧАСТЬ 2. ПРОВЕРКА ПРОЕКТА ПЕРЕД СДАЧЕЙ

Выполнять из активированного виртуального окружения.

2) Проверка стиля кода PEP 8 (без ошибок, код возврата 0):

   Если команда flake8 не находится в Windows — те же шаги, что и
   для ПР2: активировать venv, установить requirements.txt, либо
   вызвать как python -m flake8 . / python -m pytest -v.

3) Проверить состояние Git:

       git status
       git log --oneline

   В истории должно быть видно не менее трёх коммитов:
       ... first commit
       ... PR2: функциональная модель на коллекциях
       ... PR3: переход к объектной модели (User, Profile, Setting, Parameter)

   Если коммит PR3 ещё не сделан — выполнить перед защитой:

       git add .
       git commit -m "PR3: переход к объектной модели (User, Profile, Setting, Parameter)"
       git push

--------------------------------------------------------------
2. Схема объектной модели (композиция)
--------------------------------------------------------------

    User (id, username, email)
      │  создаёт
      ▼
    Profile (id, user, name, description, settings: List[Setting])
      │  содержит
      ▼
    Setting (id, profile, category, parameters: List[Parameter])
      │  содержит
      ▼
    Parameter (id, setting, key, value, value_type, default_value,
               min_value, max_value, allowed_values)

Каждый дочерний объект хранит ссылку на родителя (profile.user,
setting.profile, parameter.setting) — это и есть композиция
("часть-целое"): Setting не существует без Profile, Parameter не
существует без Setting.

--------------------------------------------------------------
3. Сценарий живой демонстрации (что вводить в меню)
--------------------------------------------------------------

Запустить: python main.py

  Выбор "1"  → показать список профилей — вызывает
               Profile.__str__(), видно, что профиль выводит своё
               имя и владельца (объект User внутри Profile).

  Выбор "2"  → ввести ID профиля → показать список его настроек —
               Setting.__str__(), демонстрирует Profile.find_setting
               / обход profile.settings.

  Выбор "3"  → ввести ID настройки → показать параметры —
               Parameter.__str__(), демонстрирует
               Setting.find_parameter / обход setting.parameters.

  Выбор "6"  → изменить значение параметра: сначала ввести
               заведомо недопустимое значение (например, за
               границей min/max) — показать, что
               Parameter.is_valid_value() вернул False и значение
               не изменилось (Parameter.update_value отклонил
               значение); затем ввести допустимое значение —
               показать, что значение обновилось. По окончании
               вывести строку "[LOG] Вызов create_new_setting..."
               (или соответствующую для этого сценария) —
               демонстрация декоратора @log_call из utils.py,
               оборачивающего пользовательские сценарии.

  Выбор "4"  → добавить новую настройку профилю — демонстрирует
               Profile.add_setting и декоратор @log_call на
               create_new_setting.

  Выбор "5"  → добавить новый параметр настройке — демонстрирует
               Setting.add_parameter и валидацию типа через
               Parameter.validate_type() (staticmethod).

  Выбор "7"  → сбросить параметр к значению по умолчанию —
               Parameter.reset_to_default(), также обёрнуто в
               @log_call.

  Выбор "0"  → выход с сохранением всех объектов в JSON (data/*.json)
               через storage.py — показать, что объекты сериализуются
               обратно в JSON и данные сохраняются между запусками.

5. Краткие ответы на контрольные вопросы (по категориям)
--------------------------------------------------------------

### Классы и объекты

Q: Почему выбрана именно такая композиция классов?
A: Она напрямую отражает предметную область: пользователь создаёт
   профили, профиль объединяет настройки, настройка объединяет
   параметры — естественная иерархия "часть-целое", не наследование.

Q: Как связаны объекты между собой?
A: Через ссылки: Profile хранит объект User (user), а также список
   объектов Setting (settings); Setting хранит ссылку на свой
   Profile и список объектов Parameter; Parameter хранит ссылку на
   свой Setting. Это композиция, а не наследование.

### Принципы ООП

Q: Используется ли наследование?
A: В данном проекте — нет, используется композиция ("has-a"), она
   лучше подходит модели "профиль состоит из настроек". Все четыре
   класса самостоятельны и не образуют иерархию наследования.

Q: Где применяется инкапсуляция?
A: Логика изменения состояния вынесена в методы классов:
   Parameter.update_value() и Parameter.is_valid_value() — контроль
   допустимости значения происходит только внутри класса, внешний
   код не модифицирует parameter.value напрямую в обход проверки.

### Методы и декораторы

Q: Чем отличаются @staticmethod и @classmethod в проекте?
A: Parameter.validate_type() — @staticmethod: не использует ни сам
   класс, ни экземпляр, это чистая функция проверки типа значения,
   логически относящаяся к классу Parameter. User.from_data() —
   @classmethod: принимает cls и создаёт новый экземпляр User из
   словаря данных (загруженного из JSON), то есть использует класс
   как фабрику объектов.

Q: Что делает пользовательский декоратор log_call?
A: Он оборачивает функцию-сценарий (например create_new_setting,
   reset_parameter) и перед/после её выполнения печатает в консоль
   строку вида "[LOG] Вызов <имя функции>...", не изменяя логику
   самой функции — демонстрирует общий принцип работы декораторов
   (функция, принимающая и возвращающая функцию).

Q: Зачем в models/profiles.py и settings.py используется
   TYPE_CHECKING?
A: Чтобы избежать циклического импорта между модулями (Profile
   ссылается на тип Setting, Setting ссылается на тип Profile) —
   импорт для аннотаций типов подключается только во время проверки
   типов (mypy/IDE), а не во время выполнения программы.

### Индивидуальный проект

Q: Что изменилось по сравнению с ПР2?
A: Функции и словари заменены классами: User, Profile, Setting,
   Parameter. Связи по числовым id (setting_id, profile_id) в
   словарях заменены прямыми ссылками на объекты
   (parameter.setting, setting.profile, profile.user). Добавлены
   методы классов вместо отдельных функций, работающих с
   коллекциями словарей. Добавлен декоратор log_call и разделение
   staticmethod/classmethod.

Q: Как теперь устроено хранение данных?
A: storage.py при загрузке преобразует JSON (списки словарей) в
   объекты классов, восстанавливая связи между ними (например,
   parameter.setting = найденный по id объект Setting); при
   сохранении выполняется обратное преобразование объектов обратно
   в словари для записи в JSON.
